## 1. 结论与优先顺序

**还有值得优化的地方。** 持续帧率优先查云步进 / 全屏拷贝、雨碰撞的场景捕获;雷击期间的卡顿查分叉对象创建和点光源。先区分主线程、渲染线程与 GPU 瓶颈,再选对应项,不能仅凭代码判断 GPU 一定是瓶颈。

当前雨默认 **10 万粒、配置上限 40 万粒**,碰撞与水花默认关闭。主默认云光样本 **25**,另一默认层为 **5**;已有 XML 可能不同。每个雨相机独立持有资源并执行模拟与绘制,因此附加相机会放大开销。

P1 表示优先测量 / 试做,P2 表示根据结果继续,P3 表示顺手处理。表中“改动”是后续实施范围,本次只写文档。

| 优先级 / 编号 | 优化项 | 收益出现的场景 | 改动 / 主要代价 |
|---|---|---|---|
| P1 · C1 | 调低云光采样预算 | 厚云、云内、GPU 光步进耗时明显 | 现有参数即可 A/B;自阴影质量变化 |
| P1 · C2 | 减少全屏拷贝、共享场景深度历史 | 高分辨率、多云层、多相机、带宽受限 | C# RT 生命周期调整;时序历史风险 |
| P1 · R1 | 减少雨碰撞深度捕获工作 | 复杂地形 / 建筑 / 机体、PIP | 先量两次捕获;缓存方案复杂、须处理失效 |
| P1 · R2 | 仅碰撞时跳过水花旧位置路径 | 碰撞开、水花关、大雨量 | C# + compute;省访存,仍需当前帧碰撞 |
| P1 · R3 | 去掉 `FillArgs` 的全量原子计数 | 所有正常雨视图,雨量越大工作越多 | 可先只改 C# 写已知数量;实际收益待测 |
| P1 · R4 | 完全透明时停止雨视觉管线 | 透明度为 1、仍需雨声 | C# 门控与恢复;普通可见雨无收益 |
| P1 · L1 | 修正雷光配置应用,再控制照亮范围 | 雷光闪烁、周围可受光物体多 | C# 初始化顺序;照亮范围会变化 |
| P2 · L2 | 分叉池化、集中更新,按需合批 | 雷击生长 / 消退时出现帧时间尖峰 | C# 对象生命周期;合批还需保持朝向 |
| P2 · C3 | 云带区间裁剪,跳过空域 | 薄云带、高空 / 远距斜视 | Shader 改造;高斯尾部、TSS 风险 |
| P2 · C4 | 光照密度简化、噪声 LOD | 云密度采样占 GPU 大头 | Shader / 纹理改变;可能影响云形 |
| P2 · R5 | 雨可见实例压缩、PIP 独立预算 | 雨顶点处理或多视图成本明显 | 索引 buffer / compute / 配置;不是直接减绘制数量 |
| P2 · C5 | 反射云独立分辨率、减少回写 | 开启水面反射云时 | C# RT / 合成调整;主视图无直接收益 |
| P3 | 缓存 pass / 属性 ID、小数组及指标 | CPU 调用或 GC 经测量确实明显 | 改动小,通常不能代替渲染预算优化 |

建议先做同场景 A/B 确认瓶颈。低改动验证可从 **C1、R3、L1** 开始;若开启碰撞后掉帧明显,先量 **R1 / R2**;云合成或带宽占比高时做 **C2**。无需一次实施整表。

## 2. 云渲染

### C1. 用现有参数降低光照采样预算

- **证据**:`Clouds/CloudConfig.cs:309、373` 的两个默认值为 25 / 5。`Clouds/Shader/Clouds.shader:568、575、686` 中有效主射线样本进入光步进,每个光样本再算一次密度。独立 `lightStepSize` 和按壳内长度缩短光步进均已实现。
- **操作**:保持 `lightMarchDistance` 不变,同一场景比较 25 / 12 / 6;先改测试预设,不直接覆盖所有用户 XML。步数下降会使光步长增大,实际循环次数也受壳长限制,不能把 25→12 当作 GPU 总成本减半。
- **验证**:厚云内部、逆光、晨昏、薄云边缘,记录 GPU 帧时间和图像差异。空天或 CPU 受限时收益可能很小。
- **限制**:已有配置值与旧默认相等不代表用户未修改;不能据此自动迁移配置。TSS 已降主射线分辨率,关闭 TSS 会提高该分辨率且保留部分时序流程,不能当成通用加速开关(`Clouds/CloudLayerView.cs:66`)。

### C2. 减少全屏拷贝和重复历史

**证据**:`Clouds/CloudRenderer.cs:816–818` 每个体积云层有三次历史写回;`:823–824、857` 合成首尾各有一次额外整图复制。`Clouds/CloudLayerView.cs:75–78` 的上采样结果和三张历史均为全分辨率。

按风险拆成三个实验:

1. **合成链首尾直接连接**:第一层直接读 `source`,最后一层直接写 `destination`,中间层保留交替 RT。处理无有效层的直通,避免同一 RT 同时读写。
2. **颜色历史交换 + 相机公共场景深度历史**:用双缓冲交换代替颜色复制;同一相机各层读取的 `combinedDepthTex` 相同,可由每相机保存一份上一帧场景深度。各层仍保留独立历史有效性,云层停用 / 重新进入体积路径时须重置。
3. **云深度历史降分辨率**:当前把低清云深度放大全清保存。可另行评估低清历史,但这会改变边缘插值 / 历史拒绝行为,不能当成无损删除。

**验证**:单层 / 双层、PIP、相机快转、建筑遮挡边缘、改分辨率、切 TSS、纯轨道返回地面和浮动原点。保留 `CloudRenderer.cs:798` 已记录的上采样路径约束,不要顺便恢复失败过的双 MRT 方案。

### C3. 云带区间求交,减少空样本

- **证据**:`Clouds/Shader/Clouds.shader:610–629、668、699–707` 仍在地表至 `maxCloudHeight` 壳内步进,最多 350 次;连续空样本只触发步长加倍。
- **方案**:沿用 [云带区间提案](cloud-band-interval-raymarch-2026-10-03.md) 的求交与区间排序思路,把预算集中在可能存在密度的区间。带内厚云不一定受益。
- **先决问题**:密度高斯项(`Clouds/Shader/Clouds.shader:456–457、543–544`)没有硬边界。直接按 `height ± spread` 裁切可能损失尾部,必须先定义保守密度上界或可接受误差阈值,再结合 coverage 和实际密度公式推导边界。
- **验证**:薄卷云、地平线、穿越层带、云面深度、反射和 TSS;边界 / 开关变化清历史。旧提案“近似零风险”不能作为实施依据。

### C4. 密度采样与 3D 噪声 LOD

`SampleDensityCheap` 仍包含两次 3D 噪声、domain warp、球坐标三角函数、行星贴图、可选 stock cubemap 及四通道高斯计算(`Clouds/Shader/Clouds.shader:471–553`),并被每个光样本调用(`:575`)。

- **先试光照专用简化密度**:在不改变主射线云形的前提下,单独降低阴影查询细节。细节噪声参与最终密度,直接删除仍会改变阴影;不能承诺无视觉损失。
- **再试噪声 mip / 距离 LOD**:`Clouds/CloudNoise.cs:33–41` 的 3D R8 纹理没有 mip;密度采样仍固定 `SampleLevel(...,0)`。生成 mip 后还要按步长 / 距离选 LOD,平均化噪声经非线性阈值可能改变覆盖率。主要用于远距稳定性和带宽实验,不保证仅打开 mip 就更快。
- **LUT / 光照体放后面**:LUT 可能用带宽换 ALU;光照体还要每帧构建,改动和质量风险更大。先证明当前瓶颈值得承担这些成本。

云密度修改必须核对完整 / 廉价 / 轨道 / 反射消费点,保留同源性或明确质量差异。

### C5. 水面反射云

**已实现**步长 ×5、光样本 2、独立材质且不走 TSS(`Clouds/CloudReflectionRenderer.cs:56–57、173–185`);`WaterReflection` 默认关闭。

剩余机会在 `:242–251` 云 RT 与反射 RT 同尺寸,以及 `:203–205` 每层合成后整图回写。可加反射云自身分辨率比例,跨层交替合成后只回写一次;静态材质属性可按配置版本更新。验证海面云倒影、地平线、快速转向和开关恢复。降低刷新频率需要处理视角变化,不能每隔几帧直接复用旧投影图像。

## 3. 雨、碰撞与水花

### R1. 优先测量两次碰撞场景捕获

**证据**:`Weather/Rain/RainCollision.cs:150–162、203` 每个有效雨相机每帧做 tagged 捕获,再按掩码对 26/29/31 层做无标签捕获,最多两次场景剔除 / 几何提交。碰撞图 512→256 会把像素数降到四分之一,但 CPU 剔除和几何提交不按该比例下降。

实施顺序:

1. 分别测 tagged / physical 捕获、Prepare / Resolve 和雨 / 水花绘制;确认成本来自场景、粒子数还是填充率。
2. 掩码为空时可省对应捕获,但首遍负责清色与深度;跳过后必须显式保持清屏语义。非零掩码不代表视野中一定有几何,也不能直接判为空。
3. 若捕获确实主导,评估静态地形深度缓存与动态物体每帧捕获。分层标签不能直接当作静态性证明;缓存还需覆盖相机位移 / 朝向、雨域半径、地形 LOD、移动平台和浮动原点的失效。

**约束**:不能把两遍简单恢复成一遍 `RenderType` 捕获。游戏地形 / 机体 / 建筑 shader 没有该标签,这是此前水花不可见的已确认根因。也不能因为面向海面就跳过几何,附近仍可能有甲板或建筑。

### R2. 水花关闭时省掉旧位置快照

**证据**:`Weather/Rain/RainCollision.cs:201–202` 仍按粒子容量执行 Prepare。`Weather/Rain/Shader/RainCollision.compute:102–105、123、129–134` 即使水花关闭,仍写 / 读上一帧位置,对已穿表面的粒子再查询旧位置表面。

旧位置路径用于判定真实穿越并生成水花。仅碰撞时可直接按当前表面裁剪 / 回收,跳过全量快照和旧位置查询;水花池只需在关闭时清理残留。10 万粒时可省一轮 10 万条位置快照及相关查询,**仍保留深度捕获和当前帧碰撞**。

验证仅碰撞不穿地 / 屋顶、水花开关无旧池残留、刚重生粒子不误触发、暂停及重定位。改变 compute 后须重新编译 / 打包并进游戏核对。

### R3. 去掉已知数量的全量计数

**证据**:`Weather/Rain/RainParticles.cs:1098–1099` 已知道 `amount`(普通模式为容量,TestRow 为 20);`:1127、1166–1169` 却每帧清 `args[1]` 并 dispatch。`Weather/Rain/Shader/RainParticles.compute:209–214` 只对每个 `id < amount` 原子加一,没有真正的可见性 / 存活剔除。

可先由 C# 在数量或缓冲变化时写 `args[1]`,停止清零与该 dispatch;保留旧 kernel 也能验证,这一阶段可不改资源包。若进一步删除 kernel / 绑定则须同步打包。结果仍为 `amount`,碰撞隐藏行为保持由 shader 处理。

当前默认省去每相机每帧 10 万次同地址原子及一次 dispatch,上限配置为 40 万次;这些是操作计数,不是耗时估计。旧审计因“未来会剔除”而禁止 CPU 写数量,不适用于当前实现。若后续做 R5 的真实压缩,须改为 GPU 生成可见数量。

验证 10 万 / 40 万、TestRow 往返、容量变更、多相机、碰撞隐藏和零 / 极低配置的 clamp 行为。

### R4. 完全透明时停掉视觉工作

`Weather/Rain/RainParticles.cs:1045、1104–1169、1228–1240` 当前只按环境淡出早退。透明度 1 令雨和水花 alpha 为零,仍运行粒子模拟、碰撞捕获与绘制。

在**完全透明**时增加视觉停工,继续更新主视图环境量和雨声;不要把透明度并入共享声音淡出。恢复时重置位置 / 碰撞历史,避免冻结状态突然显露。该优化只帮助主动隐藏雨视觉的场景,不降低普通可见雨的成本。

### R5. 可见实例压缩与附加相机质量档

- **证据**:`Weather/Rain/RainParticles.cs:1231–1239` 提交全域实例;`Weather/Rain/Shader/RainParticles.shader:168–186` 的碰撞隐藏发生在顶点阶段,并未从实例列表剔除。正常 10 万粒 × 每粒 8 顶点是值得测量的绘制规模。
- **可见列表**:保留全域模拟,只把视锥内 / 未隐藏粒子的索引写入绘制列表;shader 用列表映射回原粒子。新增剔除 dispatch、buffer 与间接计数也有成本,必须确认顶点处理占比后再做。单纯减少 `instanceCount` 会遗漏任意一段粒子,不等于正确剔除。
- **PIP 预算**:按附加相机分辨率设置雨量 / 碰撞图质量,保留每相机独立资源;不能直接缩小全局静态配置影响主视图。先用现有 `ExtraCameraRain` / `ExtraCameraClouds` 开关做开关对照,确认附加视图增量。
- **验证**:雨量密度、镜头快转、世界系构轴、遮挡、不同朝向的 PIP、主视图雨声与诊断量归属。

水花已经有 **2048 槽、每帧最多 128 次发射请求获准尝试入池** 的预算。固定绘制空槽仍有顶点工作,但规模远小于雨滴;先测再决定压缩。近景水花片元中的 `atan2/cos/pow` 可比较预烘纹理,也不应先认定为主瓶颈。

## 4. 闪电:改善雷击时的帧时间

### L1. 先修实际光源没有应用配置

**已由源码确认的缺陷,尚未修复**:

1. `Weather/Lightning/LightningModule.cs:449` 调用 `LightningBolt.Create`。
2. `LightningBolt.cs:143、208–211` 在 Create 内先 Build,使用默认字段创建点光源,范围为 **8000 m**、强度为 **8**。
3. `LightningModule.cs:457–458` 随后才给 bolt 字段赋配置;当前没有再次写入 `_light.range` / `_light.intensity`。

因此仅调小配置 `lightRange` 当前不能改变真实光源。后续应在 Build 前传入配置或显式应用光源设置,先验证实际 Light 值,再比较较小范围的夜间效果和渲染成本。无阴影也可能有附加受光成本,收益取决于实际渲染路径 / 材质 / 可受光物体,只在雷光亮起期间出现。

### L2. 分叉池化、集中寿命管理与合批

`Weather/Lightning/LightningBolt.cs:375–381、568–617、725` 在生长过程中陆续创建分叉 GameObject、LineRenderer 和 SelfDestruct,然后销毁。总数为 `(arcs−3)×(splits+1)`,默认 **85**、最大配置 **549**;不是都在同一帧生成。

先用对象池和集中寿命更新减少生长 / 销毁尖峰,再用 Frame Debugger 确认是否需要少量 ribbon Mesh 合批。**分叉材质已共享**,Renderer 数量不能直接当作实测 DrawCall 数。

合批须维持视线朝向、渐变 / 亮度和多相机效果。回归暂停停表、浮动原点、分叉起点、消退、离场清理及材质所有权。该项主要改善雷击期间的高分位帧时间,未必改变无雷时平均 FPS。

## 6. 怎样确认真正改善了帧数

本次没有新的运行时测试。既有 **135 项 GPU 功能验证**证明对应功能行为,不提供性能结论。

1. **基准条件**:固定构建、行星 / 场景、分辨率、画质、镜头路径、天气、雨量、VSync / 帧率限制和 PIP 数量。预热后每档采样至少 30 秒、重复 3 轮;使用固定预设 / 可复现天气,记录随机性。记录帧率限制是否掩盖了耗时差异。
2. **先拆模块**:同一地面场景依次比较云关 / 开、雨单独开启、碰撞 256 / 512 且水花关、再开水花;之后单独比较 PIP 与雷击。一次只改一个变量,不必直接跑完所有组合。
3. **指标**:帧时间平均值、P50 / P95 / P99;主线程 / 渲染线程 / GPU 毫秒、GC Alloc、实际 DrawCall。重点项再看各 pass / compute dispatch,雷击记录生长、闪光、消退阶段的尖峰。
4. **覆盖场景**:复杂地面 / 移动机体、海面、云内、远距薄云、轨道过渡与纯轨道;对命中的优化补相机快转、PIP、浮动原点、暂停和开关恢复。
5. **工具边界**:`Assets/Scripts/VolkenTests/Profiler/ProfilerSession.cs:27、98` 的 `CloudRenderInfo` 是配置摘要,`:168–195` 是整帧 timing;当前没有平均云步数、云专属 GPU 时长。可用现有工具做整帧 A/B,在可连接的 Unity Profiler / GPU 捕获环境中量阶段,缺失数据明确记为不可用。新增测量用可控标记,不恢复每帧日志或同步 GPU 回读。
6. **验收**:改善应跨多轮重复出现、超过基线波动;记录视觉取舍与内存变化。C# 变更先编译,shader / compute 变更还需编译、打包与游戏资源验证。结果表至少包含“场景、配置、改前 / 改后平均和 P95、GPU 数据可用性、视觉结论”。
