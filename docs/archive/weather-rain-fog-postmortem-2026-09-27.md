## 3. 四层根因

### 3.1 第一层:物理 / 概念错(真正的错)

**㈠ 长度轴在错误的空间里表达 —— 决定性错误**

一个细长 billboard 的"长"必须在**屏幕平面内**表达。旧实现用「世界空间长度轴 L + 任意与 L 垂直的宽度轴 W」构造粒子四边形。
后果:L 一旦接近视线方向(俯视/仰视/雨丝朝相机飞),**透视把 L 压成 0 而 W 完整**,屏幕上就是一块"横块"。

真机日志实测(§10.4):

```
Rain.Streaks: **真实屏幕倾角=37.4°**(0=垂直,→90=横) 沿视线分量=0.000 | 屏幕长 2.50m 宽 0.050m 长宽比=50.0
Rain.Streaks: **真实屏幕倾角=90.0°**                    沿视线分量=0.000 | 屏幕长 8.75m 宽 0.050m 长宽比=175.0
```

**同一条代码**可以产出 `2.50m / 倾角 37.4°`(接近正常雨丝)和 `8.75m / 倾角 90°`(整屏横块)——
这就是"多轮修不好"的物理来源:**错误是视角相关的,换一个视角就换个症状**。

**㈡ 「长度轴」与「宽度轴」的职责被混用**

- **长度(朝向)轴**只应由**物理量**决定:相对气流方向(重力 + 风 − 玩家速度);
- **宽度轴**应由**视线**决定:**`W = normalize(cross(L, viewDir))`**。
- 混用的两种死法:
  - W 取"世界某个固定上向量" → 视线转到与它平行时 W 退化,**宽度方向变成噪声**;
  - L 掺入相机相关量 → 雨丝随相机**横向漂移**。

**㈢ 沿视线的方向分量对屏幕方向的贡献恒为 0 —— 归一化后方向会消失**

日志里的 `沿视线分量=0.000` 不是巧合,是几何必然。因此"把归一化方向投影到屏幕求长度轴"这条路在数学上就退化:
当 `dir ≈ viewDir` 时,`dir - (dir·view)view ≈ 0`,`normalize` 放大的是浮点噪声 →
**屏幕方向随机 → 表现为径向爆散(starburst)**。

→ **正确做法(基于本轮证据推导,尚未在真机验证)**:不要从 3D 归一化方向"求"屏幕方向,
而是**直接在屏幕平面里构造长度轴**:

```
d2 = (dot(气流方向, camRight), dot(气流方向, camUp))     // 气流方向 = 重力+风−玩家速度,不归一化也可
if (length(d2) < eps) d2 = (0, -1)                        // 退化 → 竖直下落,而不是交给噪声
L  = camRight * d2.x + camUp * d2.y                       // 屏幕平面内的长度轴
W  = normalize(cross(L, viewDir))                          // 宽度轴由视线决定
```

关键点:**沿视线的分量天然被点乘丢掉,退化情况被显式兜底**,不需要 `normalize` 一个近零向量。

### 3.2 第二层:API / 坐标系错(容易查,但很费时)

| # | 错误 | 症状 | 正确做法 |
|---|---|---|---|
| ㈣ | 用**参考系空间**的视锥平面剔除**相机相对空间**的粒子 | 剔除整体错位 | 相机相对空间 + 手工构造视锥平面(`Rain.BuildCameraPlanes`);**不要**混用 `GeometryUtility.CalculateFrustumPlanes` |
| ㈤ | 用 `Camera.velocity` 当**玩家速度** | 瞬移/跟随时不真实 → 朝向乱 | 两个速度分开:朝向用**减玩家速度**,域内平移用**减相机速度** |
| ㈥ | `LeanGain` 乘在**未归一化**的方向上 | 增益被风速量级吞掉/放大 | 增益乘在**归一化方向**上 |
| ㈦ | 材质 uniform 是**全局的**,多相机共享同一 `Material` | 后一个相机覆盖前一个 → 朝向随相机跳 | **每次绘制前**按当前相机重设基向量与相机相关 uniform |
| ㈧ | 全局调试开关用**实例字段** | dev 命令写的实例 ≠ 实际绘制的实例 → "开了等于没开" | 调试开关必须 `static` |

> ㈧ 有个同源变体:`_activeInstance != this` 守卫本来是给**静态转发**写的,
> 后来改成**实例** `OnPreCull` 后,该守卫把 100% 的回调挡掉 → `draws=0`。
> 真机日志:`rfc/s: calls=82 notActive=82`。**实例与静态混用时,守卫必须跟着改。**

### 3.4 第四层:方法论与过程(真正致命的一层)

**㈠ 诊断量错了对象 —— 本轮最贵的错**

用**世界空间**的夹角当"屏幕倾角",连续多轮定位不到真正的问题(§10.4 F~I)。
诊断必须量**你真正关心的那个量所在的轴**:
关心"屏幕上看起来像不像雨丝",就量**屏幕空间**的倾角、屏幕长宽比、沿视线分量。

**㈡ 诊断无法区分两类根因**

`fade` 恒 0 时,"**从没被触发**"和"**触发了但被反复重置**"是两种完全不同的成因,
但只打一个 `fade=0` 分不出来 → 于是必须把**内部状态**打出来(§10.2 ㉘):

```
fadeState: target=1.000 from=0.000 elapsed=1.03/1.00 dt=0.0156 shutdown=False
```

**㈢ 日志刷屏把真错误淹没**

一次 `Group-Object` 去重就能定性,却因为没有去重而多花了一整轮(§10.2 ㉟)。

**㈣ 缺少"单行阈值判据"**

后期才建立起:回读 GPU 侧的 `instanceCount`,**一个数字直接指向阶段**并在 GPU 侧 10 秒回读一次(§10.8 ④):

| instanceCount | 结论 |
|---|---|
| `indexCount == 0` | mesh / index buffer 异常 |
| `instanceCount == 0` | **剔除或参数环节**有问题(视锥判定 / 原子计数 / buffer 绑定) |
| `> capacity` | 计数器或 buffer 绑定异常 |
| `≈ active` | GPU 侧正常 → 问题在**绘制 / 着色**(参数 buffer 没被 shader 用上 / 实例索引取错) |

**㈤ "排除法"没被及时用上**

`Camera.onPreCull` 从不触发这件事,本可以**通过"让其余一切可证明相同、只观察哪一条路径的计数在涨"**
一次定性;实际是绕了很久才做到(靠累计计数器 `calls=82 notActive=82`)。

**㈥ 缺"黄金日志"基线**

如果有"**上一版正确画面时的关键数字快照**",回归判定就是客观比较,而不是"我感觉这次好像好一点"。

**㈦ 没有停止条件**

在**两次修正之间没有任何一次可信的改善信号**的状态下继续修正 —— 这是最终放弃的直接触发点。

**㈧ 把独立性做丢了**

雨与雾是**独立特性**,理应分别可关/可回退。

## 5. 铁律(重做时的硬约束)

### 5.1 坐标系与物理量

1. **长度/朝向轴只由物理量决定,宽度轴由视线决定** —— 混用必错。
2. **细长 billboard 的"长"必须在屏幕平面内表达** —— 世界空间长度轴 + 任意宽度轴是错的。
3. **沿视线的方向分量对屏幕方向贡献恒为 0** —— 归一化近零向量 = 噪声,必须显式兜底退化情况。
4. **观感由投影决定,不由世界空间几何决定。**
5. **明确每个量的空间**:粒子存哪个空间、视锥平面哪个空间、相机相对还是参考系。**不许混。**
6. **两个速度不许混**:朝向用玩家速度,域内平移用相机速度;`Camera.velocity` 不能当玩家速度。
7. **增益(lean/gain)必须乘在归一化方向上。**
8. **参数必须与参考实现标定,并同时算两个数**:
   - 目标密度(个/m³)= `粒子数 / 域体积`;
   - 停留时长(s)= `域直径 / 相机速度`;
   - 两者**同时满足**才有"看起来一直在下雨"。

### 5.2 架构与生命周期

9. **每帧都会调到的路径里,禁止出现"重置动画进度"的副作用。** 重入守卫只能看**目标值**。
10. **守卫只能读状态,不能挡在"改状态的逻辑"前面** —— 否则状态机被自己的守卫锁死。
11. **状态标志必须幂等**:`Shutdown` 一类请求标志要在闸门重开时复位,否则特性**永久失效**。
12. **`Update` 链路必须每帧把外部状态推进来** —— "只在初始化/加载时同步一次"必然漏。
13. **多相机共享材质 uniform**:每次绘制前重设相机相关 uniform。
14. **全局调试开关必须 `static`**;实例/静态混用时,守卫要跟着改。
15. **一次性把同类资源的全部用法换成同一套语义**(别按报错一条条修)。

### 5.3 诊断

16. **诊断必须量你真正关心的那个量所在的轴**(屏幕问题就量屏幕)。
17. **诊断必须能分开"从没触发"与"触发后被重置"** —— 输出**当前值 + 内部状态**。
18. **日志按消息去重后再统计次数**;**优先用累计计数器**而不是节流日志。
19. **每个诊断项都要有一个"单行阈值判据"**,看到一个数字就能指向阶段。
20. **保留黄金日志(数字基线)**;回归判定用数值比较,不用感觉。
21. **先做"排除法"**:让其余一切可证明相同,只观察哪条路径的计数在涨。

### 5.4 流程

22. **跨界移植先收约束**:坐标系 / 事件 / 资源加载 / 编译行为,各写一条最小复现验证,再写业务代码。
23. **别一次写 2000 行再调** —— 最小可运行版(能出一根雨丝)→ 参数标定 → 数量级 → 观感。
24. **先标定数量级,再调观感**:密度、域半径、停留时长、视野内粒子数,先算出来再调。
25. **设停止条件**:同一问题**连续 3 轮**没有可信的改善信号 → 停下来换方案或缩减范围,不许原地继续修。
26. **特性之间保持独立可回退**(雨与雾本就应分别可关)。
27. **诚实登记"没有收敛的事"** —— 不要让"能编译"伪装成"已完成"。

## 6. 已证伪的思路清单(不要再试)

按"症状 → 为什么不行"记,避免重做时重复走一遍:

| 试过的做法 | 症状 | 为什么不成立 |
|---|---|---|
| 长度轴 = 世界固定基(如世界 up) | 视角退化,雨丝朝任意方向倒 | L 与视线平行时投影为 0,宽度接管屏幕 |
| L 掺入 `Camera.velocity` | 雨丝**横向**,且随相机移动漂移 | 相机速度与雨的物理朝向无关 |
| L = `normalize(airDir + lean·某方向)` 后投影求屏幕方向 | **径向爆散**(starburst) | 沿视线分量贡献恒为 0,归一化放大噪声 |
| 只把 `LeanGain` 去掉/调小 | 症状减轻但不消失 | 根因是空间选错,不是增益大小 |
| 换坐标系(参考系 ↔ 相机相对) | 症状换个样子出现 | 剔除空间对了,但长度轴仍在世界空间 |
| 只修 `InterlockedAdd` | 紫色照旧 | 同一根因还有 `Load4` 一处未修 |
| 调粒子数量 / 画质档 | "时有时无"略有改善 | 真因是**密度不足**(0.0382 vs 0.139)+ 域半径相对相机速度太小 |
| 用世界空间夹角做诊断 | 多轮定位不到 | **诊断量错了轴** |
